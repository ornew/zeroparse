# Releasing

This page says what a ZeroParse release promises, which platforms and Go versions it supports, and how a release is
tagged. It is written for maintainers who cut a release and for users who decide whether to depend on one. The
vulnerability policy is in [SECURITY.md](../SECURITY.md).

ZeroParse has no tagged release yet.

## What a v0.x Release Promises

Go modules give a v0 version no compatibility guarantee. ZeroParse states its intent for each surface instead.

| Surface | At v0.x |
|:--|:--|
| The grammar language: `.zp` syntax and meaning ([specification](../spec/README.md)) | Stable in intent. A change that breaks a grammar is announced, and `zp fix` rewrites older syntax where it can |
| The API of generated Go parsers (`Parse`, `ParseAST`, the options and the error types) | Stable in intent. A generated parser carries the runtime of the generator that produced it, so regenerate it after upgrading ZeroParse |
| The module API, including the `zp` and `grammar` packages | May change in any release; changes are announced |
| The runtime module `zeroparse.dev/zp/runtime`, as generated code uses it with `zp gen -runtime import` | Judged by its protocol version (see [the runtime protocol](#the-runtime-protocol)), not by the release version |
| Compiled grammars (`.zpc`) and the bytecode: container version 8, instruction-set version 30 ([bytecode specification](../spec/bytecode/README.md)) | Unstable: may change in any release. A loader accepts only its own versions and asks for the grammar to be compiled again |
| The JSON forms of grammars and nodes | Unstable: may change in any release |
| Ready-made parsers (`zeroparse.dev/alpha-parsers`) | Not part of a release: a separate repository, used from a checkout next to this one with a `go.work` |

"Stable in intent" means that a change needs a reason and is announced; it is not the compatibility guarantee of a
v1 module.

### The Runtime Protocol

The runtime is its own module, `zeroparse.dev/zp/runtime` in the directory `runtime/`, released with the same version
numbers as `zeroparse.dev/zp`. Which parsers a runtime can serve is decided by the **protocol version**: a number that
names one state of the interface between generated code and the runtime, independent of the release version. The
interface is the exported declarations of the runtime package, the exported fields and methods of the types they
reach, and what they mean, including the encoding of the data generated parsers pass to the runtime.

- The runtime declares a constant `ProtocolN` for each protocol version N it implements.
- A parser generated with `-runtime import` refers to the constant of the protocol it was generated for, so a parser
  and a runtime that do not match fail to build (`undefined: rt.Protocol1`), never at run time.
- The protocol version increases whenever that interface changes; a test of the runtime compares the declarations
  with the ones recorded for the current version and fails otherwise. A change of meaning or data encoding that keeps
  the declarations needs the same increase, and no test detects it.

A release whose runtime keeps the protocol serves the parsers generated by earlier releases of that protocol; a release
that changes it needs the parsers regenerated. The release notes say whether the protocol changed. The header of a
generated file (`// Code generated by zp vX.Y.Z. DO NOT EDIT.`) names the version of its generator, which is how security
advisories name affected parsers.

## Version Numbers

Releases are tagged with semantic versions, `vMAJOR.MINOR.PATCH`, as Go modules require. The first release is
v0.1.0.

- Before v1, a **minor** version may change a surface that is stable in intent, with an announcement.
- A **patch** version fixes defects and changes no surface that is stable in intent.
- A release that turns out to be broken is retracted with a `retract` directive in the `go.mod` of the next release;
  a published version cannot be removed from the Go module proxy.

## Announcing Changes

Each release has release notes on its GitHub release page; the repository keeps no separate changelog file. The notes
list breaking changes first, each with what to do (including the `zp fix` rewrite where one exists), then new
features and fixes.

## Supported Platforms

| Platform | Status |
|:--|:--|
| macOS on Apple silicon (darwin/arm64) | Tested: the repository tests and the benchmarks run on it |
| Linux on x86-64 (linux/amd64) | Tested by the continuous-integration workflow when it runs. Workflows are paused at present, so a release runs the checks on linux/amd64 before it is tagged |
| WebAssembly (js/wasm) | Tested: the playground's WebAssembly build has a smoke test under Node.js, which runs when Node.js is installed |
| Windows | Not tested. The module builds and passes `go vet` for windows/amd64 |
| 32-bit platforms | Not supported. The module builds for linux/386, but known integer-overflow defects on 32-bit platforms are open; the work is deferred |

Generated TypeScript is tested under Node.js: the continuous-integration workflow uses Node.js 22.18.0, and the
benchmarks run it under Node.js 24.13.0. It is written to run in Deno, Bun and browsers, but no test runs it there.

## Go Versions

**ZeroParse requires Go 1.27.1 or later, and so does the Go code it generates.** That covers the `zp` command, the engine
API and generated Go with either runtime: the default `-runtime embed`, which copies the runtime into the generated
package, and `-runtime import`, which makes the consumer depend on the ZeroParse module. Generated Go is required to build
with Go 1.27.1 or later; no lower version is promised.

**Recording `zp` as a tool raises the module's `go` line to 1.27.1.** `go get -tool zeroparse.dev/zp/cmd/zp` adds
the ZeroParse module as a dependency, and because that module requires Go 1.27.1, the `go` command raises the consumer
module's `go` line to match (`go: upgraded go 1.23 => 1.27.1`). This is expected: the generated code needs the same
version.

## Tagging a Release

In the commands below, `vX.Y.Z` is the version being released and the module path is `zeroparse.dev/zp`.

1. Check that the release items of the [project strategy](strategy.md#wedge-and-sequencing) are done.
2. The repository lives in the `zeroparse` GitHub organization, at `github.com/zeroparse/zp`, and its module path is
   `zeroparse.dev/zp`. The site serves `go-import` and `go-source` meta tags so that `zeroparse.dev/X` resolves to
   `github.com/zeroparse/X` for the repositories listed in `site/vanity.go` (see
   [Go vanity imports](site.md#go-vanity-imports)). Before the first release, check that the deployed site serves
   them:

   ```bash
   curl -sL 'https://zeroparse.dev/zp/cmd/zp?go-get=1' | grep go-import
   curl -sL 'https://zeroparse.dev/zp/runtime?go-get=1' | grep go-import
   ```

   Both print `<meta name="go-import" content="zeroparse.dev/zp git https://github.com/zeroparse/zp">`: the runtime
   module is found in the `runtime/` directory of the same repository. Also check that
   private vulnerability reporting is enabled for the repository, so that the route in [SECURITY.md](../SECURITY.md)
   works.

   The ready-made parsers are in their own repository, `github.com/zeroparse/alpha-parsers`, which the site serves as
   `zeroparse.dev/alpha-parsers`.

3. Start from a clean checkout of `main` at the commit to tag:

   ```bash
   git switch main && git pull --ff-only && git status --short   # prints nothing
   ```

4. Run the checks of the [development guide](development.md):

   ```bash
   go test -timeout=30m ./... ./runtime/...
   go generate ./bench && git status --short   # generated files are current: prints nothing
   hack/test-alpha-parsers.sh
   (cd site && go test -count=1 ./...) && site/build.sh
   ```

5. Run the checks of step 4 on linux/amd64 as well, on a Linux machine or by a run of the continuous-integration
   workflow. While workflows are paused, this run is a precondition of the release.
6. Check the figures in the README and in [Why ZeroParse](why-zeroparse.md) against the current
   [benchmark report](benchmarks.md); rerun the benchmarks only if the report is older than the changes it describes.
   From the first release, `zp gen` generates parsers with budget controls by default (today `-budget-controls` turns
   them on), and published performance figures are measured with the limits on.
7. Update the resource policy of [SECURITY.md](../SECURITY.md) to the defaults that this release ships.
8. Write the release notes ([Announcing Changes](#announcing-changes)).
9. Tag the runtime module at the commit checked in steps 3 to 5 and push the tag; the runtime requires no other
   module, so its version exists as soon as the tag does:

   ```bash
   git tag -a runtime/vX.Y.Z -m "ZeroParse runtime vX.Y.Z"
   git push origin runtime/vX.Y.Z
   GOPROXY=https://proxy.golang.org go list -m zeroparse.dev/zp/runtime@vX.Y.Z
   ```

10. Make `zeroparse.dev/zp` require that runtime version, with its checksum, in a commit of its own on `main`, and check
    that the module builds outside the workspace:

    ```bash
    GOWORK=off go get zeroparse.dev/zp/runtime@vX.Y.Z && GOWORK=off go mod tidy
    GOWORK=off go build ./... && go test -timeout=30m ./... ./runtime/...
    git commit -m "Require runtime vX.Y.Z" go.mod go.sum
    ```

    The runtime directory is the same as in the tagged commit, so the checks of step 4 still hold for it.
11. Tag that commit with an annotated tag and push it:

    ```bash
    git tag -a vX.Y.Z -m "ZeroParse vX.Y.Z"
    git push origin main vX.Y.Z
    ```

    Signing the tags (`git tag -s` in place of `git tag -a`) is optional. When workflows are enabled, pushing the tags
    starts the continuous-integration workflow. The local checks of steps 4 and 5 are the release gate either way.

12. Ask the Go module proxy for the new version, so that `go get` and pkg.go.dev see it:

    ```bash
    GOPROXY=https://proxy.golang.org go list -m zeroparse.dev/zp@vX.Y.Z
    ```

13. Publish the release notes on the GitHub release of the tag.
